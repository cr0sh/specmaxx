## What the numbers mean

specmaxx estimates the **theoretical maximum** speed of a model on a hardware stack: what the chips, memory and links allow, not what any inference engine achieves. Real engines land below it.

Every rate is quoted with the context it applies to, like **33.9 tok/s @ 8k**. Prefill @ P is a prompt of P tokens processed from an empty cache. Decode @ N is one new token generated after N tokens are already cached. A tok/s figure without its context length means nothing, because attention gets more expensive as the context grows.

More: [scope and conventions](simulation-model.md#1-scope-and-conventions), [context of each rate](simulation-model.md#pipeline-and-dp).

## From model to operations

The model is read from its Hugging Face `config.json` and turned into a list of **operations** with real shapes and number formats: matrix multiplies (projections, MLPs, the LM head), attention, norms, activations, embedding lookups, mixture-of-experts routing and, with several devices, communication. Layer types that are not plain attention (latent attention, sparse or sliding-window attention, linear-attention and state-space layers, n-gram tables) become the operations they physically need.

Each operation counts the arithmetic it needs (FLOPs) and the bytes it must read and write: each weight, cache entry and activation is touched once. The shapes depend on the batch size and on the context length of the phase being estimated.

More: [model IR](simulation-model.md#2-model-ir), [operation catalogue](simulation-model.md#3-op-catalogue).

## Hardware

A device is described by its peak arithmetic rate **per number format** (bf16, fp8, fp4, int8 and so on, with a separate sparse rate where the hardware has one), its memory bandwidth and capacity, and its links to other devices.

Peak rates are only reached by large, well-shaped matrices. Matrix units work on fixed tiles and the chip works in waves of tiles, so a small or awkward shape leaves part of the hardware idle. The estimate applies this tile and wave rounding to every matrix multiply, which is why single-token decode never reaches the headline TFLOPS. On Apple GPUs, single-token matrix-vector products run on the plain vector units without that rounding, as Apple's MLX and llama.cpp kernels do.

Presets cite their vendor sources. Some values are marked as estimated where no vendor publishes them.

More: [hardware](simulation-model.md#4-hardware), [shape efficiency](simulation-model.md#shape-efficiency), [preset library](simulation-model.md#preset-library).

## How time is computed

Each operation takes the longer of two times (the **roofline**):

- **compute time**: its FLOPs divided by the achievable arithmetic rate, and
- **memory time**: its bytes divided by memory bandwidth.

If compute is longer the op is _compute bound_, otherwise _bandwidth bound_. The time of a step is the sum of its operations (on the busiest device). Communication is added using a latency-plus-bandwidth cost, and by default the bandwidth part may overlap with compute while the latency part may not.

**Communication overlap** can also be set per kind of exchange, under Hardware → Advanced: the TP and shared lookup-table exchanges, the EP all-to-alls, and the hand-off between pipeline stages. Each takes the global setting by default, or none, full, or a partial share: that share of its transfer time may hide behind the stage's compute (never more than the compute itself), and the rest adds to it. **Two-batch overlap** (mixture-of-experts models whose EP spans DP replicas) splits each batch in two halves that alternate, so one half's all-to-all hides behind the other half's compute; it sets the EP overlap to full. The halves are costed as real smaller batches: each runs smaller matrix multiplies, reads the weights again and pays the message latencies twice, and the activation peak halves. So it helps only when the exchange would otherwise not hide; with the default ideal overlap it can only lose. Reported gains: SGLang +27–35% prefill and +25.5% decode at 256 tokens per GPU, and no gain or a loss below about 64–128 tokens per GPU ([LMSYS](https://lmsys.org/blog/2025-05-05-large-scale-ep/)); vLLM's dual-batch overlap needs DP with EP ([vLLM DBO](https://docs.vllm.ai/en/latest/design/dbo/)); SGLang turned it off on GB200 NVL72, where the exchange is small ([LMSYS GB200 part 1](https://lmsys.org/blog/2025-06-16-gb200-part-1/)). That minimum batch is a property of the engine and is not enforced here. The whole stage is treated as one overlap window, an upper bound of the layer-by-layer alternation engines run; draft models are not split, and two-batch overlap is not modelled together with offloading.

Attention also pays for its softmax: one exponential per score on the special-function units, plus a few vector operations, overlapped with its matrix multiplies. This only shows on long prompts on fast datacenter GPUs, where the exponentials can take longer than the matrix work.

Two what-if settings sit next to this. With several devices, prefill is also shown **without overlap**, as if no communication hid behind compute, since most engines do not overlap it fully. An optional **per-op latency floor** (0 by default) makes every operation take at least that long; it shows how much tiny operations could cost, but no measurement fixes its size yet.

More: [per-op time](simulation-model.md#per-op-time), [attention softmax](simulation-model.md#attention-softmax), [stage time and overlap](simulation-model.md#stage-time-and-overlap), [two-batch overlap](simulation-model.md#two-batch-overlap), [prefill without overlap](simulation-model.md#prefill-without-overlap), [per-op latency floor](simulation-model.md#per-op-latency-floor).

## Prefill and decode

**Prefill** processes the whole prompt at once. There is plenty of work per weight read, so it is usually compute bound. Its rate is prompt tokens divided by the time to process them.

**Decode** produces one token per sequence per step. Every weight and the whole KV cache must be read for very little arithmetic, so it is usually bandwidth bound, and it slows as the context grows. Its rate is one token per step time, times the batch size.

More: [pipeline and DP](simulation-model.md#pipeline-and-dp).

## Multiple devices

Work is split across devices three ways: **tensor parallel** (TP) shards each layer's matrices, **pipeline parallel** (PP) puts consecutive layers on consecutive devices, and **data parallel** (DP) runs independent replicas. Mixture-of-experts layers can also spread their experts (EP). The UI offers TP, PP, DP, for mixture-of-experts models EP, and under Advanced DCP and chunked PP prefill (below); the device count is TP × PP × DP.

**DP** runs DP full copies of the model, each on its own TP × PP devices, side by side. The batch is split evenly between them (so it must be a multiple of DP), and, without cross-replica EP or lookup-table sharing, the copies never talk to each other. In that independent case, each copy runs exactly like a single model instance serving batch / DP sequences: the aggregate rate is DP times that copy's rate, and the per-sequence rate is that copy's. Memory is checked per copy: every device holds its share of the whole model, so DP needs a model that fits on TP × PP devices. DP never makes a single sequence faster. Against TP on the same devices it trades the TP all-reduces for reading the full weights on every device: while decode is bandwidth bound TP usually gives the higher aggregate rate (each device reads only its slice of the weights), and DP wins where the all-reduces cost more than that, as in prefill, over slow networks, and at large batches ([pipeline and DP](simulation-model.md#pipeline-and-dp); `src/sim/engine/dp.test.ts`). With offloading, every copy on a machine keeps its own offloaded weights in that machine's host RAM or SSD.

**Lookup tables across DP**, under Hardware → Advanced → Offload, shares device-resident n-gram tables instead of keeping one copy per replica. Only the tables shrink; projections, token embeddings and KV placement stay independent. It adds lookup exchanges, controlled by the existing TP overlap setting. Engram at TP 1 can instead read peer memory inside a supported fully connected NVLink domain; unknown or partial connectivity uses collectives. Engram currently needs all replicas in one modeled scale-up domain (which can be an NVL72 rack, not just one server). Host RAM and SSD table placement disable sharing. The Engram all-gather and PLE all-reduce model exchange algorithms, not minimum traffic, and peer reads remain synchronous gather work ([lookup tables across DP](simulation-model.md#lookup-tables-across-dp), [approximations](simulation-model.md#9-deliberately-excluded-and-approximations)).

**EP in the UI** adds no devices. With DP = 1 it uses the TP devices: instead of slicing every expert across the TP group, each device holds whole experts: E/EP of them, each sliced TP/EP ways. So EP must divide TP and the expert count. After attention every TP device already holds every token, so no tokens are exchanged: each device runs its own experts on the tokens routed to them, and their outputs are summed by the same TP all-reduce that TP alone needs. EP therefore leaves the communication unchanged, except on models with an expert-output norm, where it removes the collectives between the devices sharing an expert. What it changes is the work per device: the busiest device gets 1.2× the mean expert work (below), it reads and writes only its own experts' token rows instead of every row, and in decode it reads whole experts (the busiest device needs ⌈tokens × top-k / EP⌉ of them). With DP > 1, EP can also span several copies: a multiple of TP that divides TP × DP. Then each device holds whole, unsliced experts and the tokens are exchanged between the copies with an all-to-all ([MoE modes A/B](simulation-model.md#moe-modes-ab)).

**DP attention + EP** is a named layout for mixture-of-experts models, the one large deployments use (vLLM's DEP, `--data-parallel-size N --enable-expert-parallel` ([vLLM](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)); SGLang's `--enable-dp-attention` ([SGLang](https://docs.sglang.io/advanced_features/server_arguments.html)); DeepSeek's EP32 and EP144, SGLang's EP72 ([LMSYS](https://lmsys.org/blog/2025-05-05-large-scale-ep/))). It is TP 1 with DP = EP = the devices of one pipeline stage (all devices without PP; EP × PP = the device count): every device runs attention for its own sequences only, so it keeps only their KV cache, and a latent-attention (MLA) cache is not copied to other devices as it is under TP. The experts are spread over all the devices of the stage, and each layer sends every token to the devices holding its experts and back with two all-to-alls. The dense layers (the non-expert feed-forward layers and the LM head) can run two ways. **DP**, the default: whole on every device, with no extra traffic (SGLang `--moe-dense-tp-size 1 --enable-dp-lm-head`). **TP**: split over all EP devices, so each holds 1/EP of their weights; the tokens of all devices are gathered before each such layer and the results scattered back after it (SGLang's default with DP attention). TP saves memory and weight reads for two collectives per dense layer; with few dense layers (DeepSeek-V3 has 3 of 61) the speed difference is small. TP needs EP to divide the dense layers' width, which the app checks ([DP attention + EP](simulation-model.md#dp-attention--ep)).

**Decode context parallelism (DCP)**, under Parallelism → Advanced, splits the KV cache by token instead of by head. TP gives each device a share of the KV heads, but there are often fewer KV heads than devices: a latent-attention (MLA) model has a single one, so under TP 8 every device holds the whole cache, eight copies. DCP splits each sequence's cache over DCP of the TP devices, so each keeps and reads about 1/DCP of it per decode step (the busiest one ⌈context / DCP⌉ tokens) and the freed memory fits more sequences. It adds no devices. The price is two small collectives per attention layer: the queries are gathered across the DCP devices before attention, and the partial results, each with its softmax normalizer, are combined and scattered back after it. Those cost mostly link latency, so DCP pays off at long context and large batches and can be slower at short context. The app requires DCP to divide TP and, for grouped-query attention, also TP ÷ KV heads (the copies of one KV head are what DCP splits); vLLM documents DCP in [1, TP ÷ KV heads] with the same divisibility ([vLLM docs](https://docs.vllm.ai/en/latest/serving/context_parallel_deployment/), [vLLM blog](https://vllm.ai/blog/2026-08-07-decode-context-parallelism)). Reported gains: Kimi-K2-Thinking on 8 × H200 at TP 8 + DCP 8 holds 8× the KV cache (715,072 → 5,721,088 tokens) and generates 43% more output tokens/s on a serving benchmark of 1,000 random requests of 8k input and 4k output tokens ([vLLM recipe](https://recipes.vllm.ai/moonshotai/Kimi-K2-Thinking)); Kimi K2.6 (NVFP4) on 8 × B200, replaying an agentic trace with a median of about 67k input and 400 output tokens, reaches 6,091 tok/s per GPU with DCP at 512 concurrent requests, where TP runs out of memory at 64 and plateaus near 1,863 tok/s per GPU (the blog above). Prefill is unchanged: it still computes the whole prompt and only the stored cache is split. Sliding-window layers keep their small cache whole, recurrent and linear-attention state is not split, and the app does not model DCP with sparse or compressed sparse attention, relative-position bias, K/V convolutions or block drafters (MTP is allowed). More: [decode context parallelism](simulation-model.md#decode-context-parallelism-dcp).

**Chunked PP prefill**, under Parallelism → Advanced when PP is above 1, splits each prompt into chunks of the prefill chunk size (8192 tokens by default, set under Hardware → Advanced → Memory fit) that pass through the pipeline stages one after another, so stage 2 works on chunk 1 while stage 1 works on chunk 2. Each chunk attends to all the tokens before it, so the total attention work is the same as for the whole prompt. Without it, a stage hands on a prompt only once it has processed all of it, so one long prompt takes the sum of all the stages' times before its first token; with it, the stages work at the same time and the time to first token drops towards 1/PP of that. The app then shows the time to first token with and without chunking under the prefill figure. The prefill rate barely changes: with several sequences in flight the pipeline is already full, and the smaller chunks run slightly less efficient matrix multiplies and read the earlier keys and values again for every chunk. Mooncake calls this chunked pipeline parallelism and uses it for long prompts across machines ([Mooncake](https://arxiv.org/abs/2407.00079)); SGLang uses chunked pipeline prefill across GB300 machines for long context ([LMSYS](https://www.lmsys.org/blog/2026-02-19-gb300-longctx/)). Engine scheduling of chunks from different requests is not modelled. Ring-attention **context parallelism**, which shards one prompt's tokens over extra devices that pass their keys and values around a ring (Meta prefilled 1M tokens of Llama-3-405B in 77 s on 128 H100 ([Meta](https://arxiv.org/abs/2411.01783))), is not modelled yet. More: [chunked pipeline prefill](simulation-model.md#chunked-pipeline-prefill).

The estimate assumes a perfectly balanced split and costs one representative device per stage. The one exception is EP: the busiest device gets more than the mean expert work, and the step waits for it ([EP load imbalance](simulation-model.md#ep-load-imbalance)). It then adds the traffic the split requires: all-reduces for TP (which also carry the expert outputs under EP), a hand-off of activations between pipeline stages, the token exchange when EP spans DP replicas, and lookup exchanges when tables are shared. A link has a bandwidth (per direction) and a latency, and a message costs latency plus size over bandwidth. Every network latency is measured the same way, half the round trip of a small-message ping-pong, so RDMA and TCP over the same cable compare fairly (RDMA is never slower).

**EP imbalance** (shown at EP > 1) is that busiest device's expert load divided by the mean device's. It scales the busiest device's expert compute; it does not change which expert weights are read (hot experts draw more tokens, not more experts). The default is 1.2 with no redundant experts. **Imbalance on all-to-all** (off by default) also applies it to the token exchange when EP spans DP replicas: on, the busiest device sends and receives its larger share; off, every device moves the mean volume, as before these settings existed. Measured values for DeepSeek-R1: 2.56 at EP 32 without a load balancer and 1.11 with one (EPLB) and one redundant expert per GPU, 288 expert slots for 256 experts ([TensorRT-LLM wide-EP blog, Table 1](https://nvidia.github.io/TensorRT-LLM/1.0.0rc3/blogs/tech_blog/blog4_Scaling_Expert_Parallelism_in_TensorRT-LLM.html), which lists (max − mean) / mean: 1.564 and 0.109); about 1.47 on 8 GPUs without one, rising with the GPU count ([SGLang large-scale EP](https://lmsys.org/blog/2025-05-05-large-scale-ep/)). So: about 1.5 (8 GPUs) to 2.5 (32 GPUs) without a balancer, about 1.1 with one. **Redundant experts** are the extra expert copies a balancer keeps on each GPU: each adds one expert's weights per MoE layer to every GPU's memory (about 2.6 GB over DeepSeek-V3's 58 MoE layers in FP8). The balancer itself is not modelled: redundant experts add memory but do not lower the imbalance on their own, so set EP imbalance to the load your balancer reaches ([EP load imbalance](simulation-model.md#ep-load-imbalance), [redundant experts](simulation-model.md#redundant-experts)).

**Dispatch format** and **Combine format** (Hardware → Advanced → Expert all-to-all, shown when EP spans DP replicas) set the number format of the two token exchanges. Their default follows the activation format (combine at least 16-bit), as before these settings existed. Each format's size counts its block scales: FP8 with a 32-bit scale per 128 values is 8.25 bits per value (DeepEP's layout), MXFP8 8.25, NVFP4 4.5 and MXFP4 4.25. Deployments differ: DeepSeek-V3 dispatches FP8 and combines BF16, SGLang and vLLM on GB200 dispatch NVFP4, and AMD's MoRI dispatches FP4 and combines FP8, which at width 7168 is 4,032 + 7,168 = 11,200 bytes per token ([DeepEP](https://github.com/deepseek-ai/DeepEP), [SGLang on GB200](https://lmsys.org/blog/2025-09-25-gb200-part-2/), [vLLM on GB200](https://vllm.ai/blog/dsr1-gb200-part1), [AMD](https://www.amd.com/en/developer/resources/technical-articles/2026/win-on-tco.html)). Only the bytes on the link change: quantising before and dequantising after the exchange is on-chip work the model does not cost, and the accuracy of narrow formats is not modelled. **All-to-all efficiency** is the share of the link speed an all-to-all reaches; it divides the all-to-all's transfer time and leaves its latency alone. It stands for the quality of the communication backend (DeepEP and similar), which the tool does not choose or model: it is your number, 100% by default (the link limit), and a rough estimate of an engine, not a hardware limit ([dispatch and combine precision](simulation-model.md#dispatch-and-combine-precision), [all-to-all efficiency](simulation-model.md#all-to-all-efficiency)).

When several tokens go through a mixture-of-experts layer at once (a batch, or a speculative verify step), the experts whose weights are read are the number expected if every token picked its experts at random. This is an expected value, not a bound: real routing often repeats experts and can touch fewer ([expected distinct experts](simulation-model.md#expected-distinct-experts)).

A PCIe link carries data in packets, and each packet's header and checksum take part of the wire. So every PCIe bandwidth here (between GPUs, to host memory for offloading, to an SSD) is the line rate times 256/280 ≈ 0.91, the payload share of full 256-byte packets. Other links (NVLink, InfiniBand, Ethernet, Thunderbolt) use the vendor's data rate. More: [PCIe payload efficiency](simulation-model.md#links-and-topologies).

Between machines the network shape matters: a switch, a full mesh, a ring or a chain. Each shape gets its own routing and bandwidth rules. Where the hardware cannot pass data straight between devices, as with some consumer GPUs, or between a GPU and a network card, the traffic is staged through host memory and pays for it. Over TCP, the operating system also copies every message into and out of its socket buffers at each end; RDMA skips that copy.

**NICs per machine** (Hardware → Advanced → Network, shown for several machines of more than one GPU each on a switch) sets how many network cards a machine has; the network link is one card. The default is one per GPU, as on a DGX B200 (8 GPUs, 8 ConnectX-7 at up to 400 Gb/s ([NVIDIA](https://www.nvidia.com/en-us/data-center/dgx-b200/))). Other machines have fewer or more: an AWS p4d has 4 × 100 Gb/s cards for 8 A100, a p5 32 cards and 3,200 Gb/s for 8 H100 ([AWS](https://docs.aws.amazon.com/ec2/latest/instancetypes/ac.html), [EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa-acc-inst-types.html)); Mooncake runs on 4 × 200 and 8 × 400 Gb/s machines, though it measures KV-cache transfers, not collectives ([Mooncake](https://github.com/kvcache-ai/Mooncake)). The GPUs of a machine share its cards evenly, since every collective here sends from all of them at once: 4 cards for 8 GPUs halve each GPU's network speed, 16 double it, up to the link's cap over all ports. A GPU never borrows another GPU's idle card, so a lone pipeline hand-off is a little pessimistic.

**In-network reduction** (same place, shown when a link in use has it) lets the switch add up an all-reduce itself instead of the GPUs passing partial sums around. NVLS (NVLink SHARP) runs on the NVLink Switch of HGX H100, H200, B200, B300 and NVL72 racks ([Hopper](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/), [NVLink](https://www.nvidia.com/en-us/data-center/nvlink/), [NCCL](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html)); SHARP runs on InfiniBand switches: SHARP on Quantum HDR ([QM8700](https://www.nvidia.com/en-us/networking/infiniband/qm8700/)), SHARPv3 on Quantum-2 NDR ([Quantum-2](https://www.nvidia.com/en-us/networking/quantum2/)), SHARPv4 on Quantum-X800 XDR ([X800](https://www.nvidia.com/en-us/networking/products/infiniband/quantum-x800/)). A100's NVSwitch, the NVL4 bridge, PCIe, Ethernet and UALink 1.0 have none. It is off by default and, when on, one more choice of the "best" all-reduce: the fastest wins, and "ring" or "tree" stay as they are. With NVLS each GPU sends and receives about (n + 1)/n of its data in 2 steps, against about twice that over 2(n − 1) steps for a ring; with SHARP each network card sends its data up once and gets the sum back once ([SHArP paper](https://network.nvidia.com/pdf/solutions/hpc/paperieee_copyright.pdf)). Caveats: the NVLS byte count is derived from how the switch works (its reduce-load and multicast-store instructions ([PTX](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html))), not stated by NVIDIA, which quotes "up to 2x" over A100. The 2 steps are a hardware floor: NCCL's own tuning model charges about 25 µs for NVLS ([NCCL tuning](https://github.com/NVIDIA/nccl/blob/v2.23.4-1/src/graph/tuning.cc)), so small decode messages gain less in practice. SHARP across machines needs NCCL's CollNet with the SHARP plugin and GPUDirect RDMA, and is off in NCCL by default ([plugin](https://github.com/Mellanox/nccl-rdma-sharp-plugins)). Multi-level switch trees and SHARP's resource limits are not modelled. More: [multi-NIC nodes](simulation-model.md#multi-nic-nodes), [in-network reduction](simulation-model.md#in-network-reduction-nvls-sharp).

A "machine" can also be a whole rack. GB200 and GB300 NVL72 join 72 GPUs through NVLink switches at 900 GB/s per GPU in each direction ([NVIDIA](https://dam-cdn.nvd.orangelogic.com/AssetLink/gl2l4l4812s5fw0p614s6i8bv6mi3vx5.pdf)); GB200 NVL4 joins four on an NVLink bridge whose layout NVIDIA does not publish, so it is estimated. AMD MI300X, MI325X and MI355X join eight GPUs with one link per pair, 64, 64 and 72 GB/s each way ([MI325X](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/product-briefs/instinct-mi325x-datasheet.pdf), [MI355X](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/product-briefs/amd-instinct-miI355x-platform-brochure.pdf)); the estimate gives every GPU the sum of its seven links, which flatters groups of two or four. A group must split the machine evenly and the experts evenly, so a 256-expert model uses 64 of an NVL72's 72 GPUs for expert parallelism.

More: [parallelism](simulation-model.md#5-parallelism), [decode context parallelism](simulation-model.md#decode-context-parallelism-dcp), [chunked pipeline prefill](simulation-model.md#chunked-pipeline-prefill), [collectives](simulation-model.md#6-collectives), [links and topologies](simulation-model.md#links-and-topologies), [scale-up domains](simulation-model.md#scale-up-domains), [rank layout](simulation-model.md#rank-layout), [fabric shapes](simulation-model.md#fabric-shapes), [host bounce](simulation-model.md#host-bounce), [inter-node host staging](simulation-model.md#inter-node-host-staging), [TCP socket copy](simulation-model.md#tcp-socket-copy).

## Does it fit in memory?

Per device, the estimate adds up the weights it holds, the cache and state for every sequence in the batch (KV cache, recurrent state), and the largest temporary activation buffer. If the total exceeds the memory the GPU may use, the setup does not fit. It also reports how many sequences would fit.

Long prompts are prefilled in chunks (8192 tokens by default), so the activation buffer is the one of a single chunk, not of the whole prompt. The prefill speed is not affected, except with chunked PP prefill on, where the same chunk is also the one that passes through the pipeline stages (above).

On unified memory the operating system lets the GPU use only part of it: about 75% on a Mac, about 50% by default on Linux with Strix Halo, nearly all of it on DGX Spark. The fit checks against that share; a raised limit can be entered under Advanced. An optional runtime reserve (framework and driver memory, 0 by default) can be added there too.

More: [memory fit](simulation-model.md#memory-fit), [activation peak](simulation-model.md#activation-peak), [GPU-usable capacity](simulation-model.md#gpu-usable-capacity), [runtime reserve](simulation-model.md#runtime-reserve).

## Offloading

Optional, off by default. Part of the weights can live in host RAM or on an SSD instead of device memory: experts of mixture-of-experts layers, or n-gram lookup tables. Each can be split by layer range, e.g. the experts of the first layers in host RAM and the rest on the SSD. Whatever is needed and not resident is fetched over the host link each step, which adds transfer time and frees device memory.

On GB200 and GB300 the host link is NVLink-C2C to the Grace CPU, taken as 450 GB/s per GPU in each direction ([NVIDIA](https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era/)); NVIDIA's wording leaves open whether a superchip's two GPUs share it. Each Grace adds 480 GB of host RAM at 384 GB/s for two GPUs ([NVIDIA](https://docs.nvidia.com/grace-perf-tuning-guide/index.html)), pooled across the machine.

The token-embedding table can move off the device too. Each token reads only one row of it, so this frees its whole size (about 2.5 GB for a 27B model) at almost no speed cost; llama.cpp keeps it in host RAM by default ([source](https://github.com/ggml-org/llama.cpp/blob/a4d4f2fd4ec85ec6a0a9ece4870416c1b6cc24f5/src/llama-model.cpp#L1780-L1782)). Models that reuse this table for their output (tied embeddings) keep it on the device.

Whole-layer offload (copying entire layers to the GPU every step) was removed: local setups don't run that way (llama.cpp computes the layers it keeps off the GPU on the CPU instead), and for a MoE model it reads every expert each step. Partial offload of dense layers would return as a CPU-compute mode, not as streaming.

Two parameters shape the result:

- **Hit ratio**: how often a needed expert is already on the device. It depends on how much is kept resident and how skewed the model's routing is.
- **Prefetch accuracy**: how often a predictor guesses the next layer's experts early enough to hide the transfer behind compute.

With both set, the result is still an upper bound given those numbers.

When one GPU reads from both host RAM and the SSD, the prefetched part of the two streams runs at the same time, limited by the PCIe link, host RAM and the SSD; experts that are only known after the router are fetched one after another.

**SSD read rate** defaults to the unchanged datasheet ceiling; the optional sustained scenario uses measured low-queue large-read fractions for expert reads, not small lookup rows. These workload-specific measurements are not a tighter proven upper bound.

**KV cache.** Part of each sequence's KV cache can live in host RAM, on the SSD or in a remote pool too: a share stays on the GPU, the rest is read back over the host link (or, for the pool, the network card) by every layer at every decode step. A larger batch or a longer context then fits, but decode slows to the speed of that link (on an RTX 5090 with PCIe 5.0, a batch of 8 at 32k context with 75% of the cache in host RAM runs at about 16 tok/s @ 32k instead of about 305). Production engines mostly use these tiers for something milder: they keep the KV of earlier prompts there and load it back once when a new request shares the prefix (vLLM's [KV offloading](https://docs.vllm.ai/en/latest/features/kv_offloading_usage/), [LMCache](https://docs.lmcache.ai/), SGLang [HiCache](https://www.lmsys.org/blog/2025-09-10-sglang-hicache/), [Mooncake](https://arxiv.org/abs/2407.00079)). That case is the "cached prefix on GPU" share, paid once at prefill. Reading only the selected tokens of sparse-attention layers each step, with the next layer's selection predicted early, follows [InfiniGen](https://arxiv.org/abs/2406.19707), [ShadowKV](https://arxiv.org/abs/2410.21465) and vLLM's [HiSparse](https://docs.vllm.ai/en/latest/design/hisparse/). A remote pool is memory on other machines shared between them ([Mooncake](https://arxiv.org/abs/2407.00079) store, [LMCache](https://docs.lmcache.ai/) remote backends, SGLang HiCache's third level): each GPU reads its share through its own network card, at the card's full speed, one network latency per fetch, and the pool is either unlimited or capped at the capacity you give. On a stack with one network, that is its link shared by the GPUs of a machine; on a single machine it defaults to one 400 Gb/s InfiniBand card per GPU, which is a little slower than PCIe 5.0 x16 (50 against 57.6 GB/s: the same batch at about 14 tok/s @ 32k). Measured pools are slower (Mooncake: 87 GB/s per machine on 4 × 200 Gb, 190 GB/s on 8 × 400 Gb, [slides](https://datatracker.ietf.org/meeting/125/materials/slides-125-irtfopen-disaggregated-architecture-for-llm-inference-mooncake-01)). Caveats: the pool's own machines and other readers are never a limit; writing new KV to any tier is not priced; sliding-window, recurrent and compressed (CSA) caches stay on the GPU.

More: [offloading](simulation-model.md#12-offloading), [expert hit ratio](simulation-model.md#expert-hit-ratio), [expert prefetch](simulation-model.md#expert-prefetch), [overlap across tiers](simulation-model.md#overlap-across-tiers), [token embedding off-device](simulation-model.md#token-embedding-off-device), [KV cache off-device](simulation-model.md#kv-cache-off-device), [host and storage tiers](simulation-model.md#host-and-storage-tiers).

## Speculative decoding

Optional, off by default. A small draft produces several candidate tokens and the full model checks them all in one step. The step costs a little more than normal decode, because it processes several positions and runs the draft, but each step can yield more than one token.

How many tokens a step yields on average follows from the **acceptance rate** you set per drafted position. The result is the tokens per step divided by the step time, and the speedup against plain decode.

The default acceptance per method and use case is fitted to published measurements, at the draft lengths they were taken at. At any other draft length the app marks the default with ⚠, because the real acceptance per position need not stay constant as the draft grows.

At large batch the check step gets expensive: it runs several positions per sequence, so its matrix multiplies hit the compute limit sooner than plain decode does. Past that point the step costs more than its extra tokens bring, and speculative decoding is slower. The batch chart shows the rate without speculative decoding next to the rate with it, and marks the **break-even batch** where it stops paying. The acceptance rate stays what you set at every batch; only the cost of the check changes.

It works with pipeline parallelism. The draft runs on the last stage; a block drafter's inputs from earlier layers travel with the normal stage-to-stage send, and the last stage keeps its own copy of the token embedding.

Not modelled: draft trees (several candidates checked at once), separate small draft models, drafting by copying from the prompt (n-gram or prompt lookup), acceptance that changes with batch, and changing the draft length on the fly.

More: [speculative decoding](simulation-model.md#13-speculative-decoding), [accepted tokens](simulation-model.md#accepted-tokens), [acceptance defaults](simulation-model.md#acceptance-defaults), [pipeline parallelism](simulation-model.md#pipeline-parallelism), [break-even batch](simulation-model.md#break-even-batch), [not modeled](simulation-model.md#not-modeled).

## Prefill/decode disaggregation

Optional, off by default. Prefill and decode run on two separate groups of GPUs (pools), each with its own hardware, parallel layout and batch, as large deployments do: DeepSeek runs prefill on 32 GPUs and decode on 144 ([DeepSeek inference system overview](https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md)), SGLang ran Kimi K2 on 4 prefill and 12 decode nodes ([LMSYS](https://lmsys.org/blog/2025-07-20-k2-large-scale-ep/), [large-scale EP](https://lmsys.org/blog/2025-05-05-large-scale-ep/)), and Mooncake, TensorRT-LLM and Dynamo do the same ([Mooncake, FAST'25](https://www.usenix.org/conference/fast25/presentation/qin), [TensorRT-LLM](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog5_Disaggregated_Serving_in_TensorRT-LLM.html), [Dynamo planner](https://docs.dynamo.nvidia.com/dynamo/v-0-9-0/design-docs/planner-design.md)).

Each pool is simulated on its own. The prefill pool gives requests per second as its prompt tokens per second divided by the prompt length; the decode pool gives its output tokens per second divided by the output length. From these the app finds the **balanced P:D ratio**, the number of prefill instances per decode instance at which neither pool waits, and the **system rate** at the ratio you set: the smaller of the two pools' request rates, as output tokens per second per GPU.

All output tokens are taken at the decode rate at the decode context you set, so these figures are quoted with the prompt length, the output length and that decode context ("533.3 tok/s/GPU @ 8k/1k, decode @ 8,704"). They are not an average over the growing context while a request generates; a decode context near the prompt length plus half the output length is a representative choice.

**KV transfer.** A finished prompt's cache (and, with speculative decoding, the draft model's cache) is sent from the prefill GPUs to the decode GPUs over a network link you choose, by default one 400 Gb/s InfiniBand NIC per GPU. By default each layer's cache is sent while the next layers compute, so the link slows prefill only when it is slower than the prefill itself; the "not overlapped" setting sends it after the whole prompt and makes prefill wait for it. The decode GPUs' own links also cap how many requests per second they can take in. The transfer uses the link's full bandwidth and one latency per transfer: no RDMA software overhead, and no cost for rearranging the cache when the decode pool splits it differently than the prefill pool. Measured transfers are slower (Mooncake: 87 GB/s per node on 4 × 200 Gb RoCE, 190 GB/s on 8 × 400 Gb, [slides](https://datatracker.ietf.org/meeting/125/materials/slides-125-irtfopen-disaggregated-architecture-for-llm-inference-mooncake-01)).

Not modelled: queueing, latency targets (SLOs), how requests are routed to instances. Disaggregation mainly helps time-to-first-token and per-token latency tails, and vLLM notes it "does not improve throughput" by itself ([vLLM docs](https://docs.vllm.ai/en/latest/features/disagg_prefill/)); here it shows the throughput bound of a given split.

More: [prefill/decode disaggregation](simulation-model.md#14-prefilldecode-disaggregation).

## Quantization

Weights, activations and the KV cache each have their own number format. Storage per element is the format's bits plus block scales and group overhead, so a 4-bit format with group scales costs a little more than 4 bits. Fractional-bit formats such as EXL3 (for example 2.5 bits per weight) are costed from their actual layout.

The format also picks the arithmetic rate. When weights are narrower than activations they are dequantized first, so the multiply runs at the wider format's rate: quantization saves memory traffic, not arithmetic.

More: [dtypes](simulation-model.md#dtypes-math-and-accumulate), [EXL3](simulation-model.md#exl3-exllamav3-fractional-bits-per-weight).

## What is not modelled

Anything that depends on a particular inference engine: paged attention, continuous batching, chunked prefill (except its effect on the memory fit and, when turned on, chunked PP prefill), scheduling and kernel-launch overhead, CUDA graphs. Also left out: dequantization arithmetic, exponentials computed on the ordinary arithmetic units instead of the special-function units (a trick some newer attention kernels use), cache reuse beyond reading each operand once, clock throttling, link contention, framework memory unless you set a runtime reserve, and request queueing and latency targets (with disaggregation too).

The one exception for engine overhead is the **engine dispatch overlay**, opt-in only and off by default. Turned on, it adds about 2 µs for launching each kernel (one per operation, nothing fused) to a decode step and shows the result as a second, labelled decode figure. The headline figure never includes it. More: [engine dispatch overlay](simulation-model.md#engine-dispatch-overlay).

The reference lists every exclusion and each approximation that remains.

More: [deliberately excluded, and approximations](simulation-model.md#9-deliberately-excluded-and-approximations).
